## 🔥 <span id="前言">前言</span>

陈泉羽项目是单一自营的虚拟商品商城，销售课程及服务，主分类为毕业论文、普刊、编译。当前处于开发阶段，直接按这一套需求、数据库、代码及测试推进。先梳理需求，再设计数据，再实现并回归；采用既定桌面、移动端、管理端、微信小程序技术路线。

## 一、<span id="source">用户原文与确认范围</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

> 对陈泉羽项目，你可能是对需求理解有偏差
> 1、我们需要做的，是有临摹目标的，本质是个商城，也就是卖课/卖服务
> 2、需要有支付，一般是接入支付宝/微信支付。但是手续还没有齐全，没办法申请下key，所以付款的时候虽然要跳出支付宝/微信支付，但是是没办法走支付流程的（暂时处理成点击以后就付款成功，等Key到来再介入真正支付）
> 3、商城类，就一定有几种商品的状态：待付款/待完成/已完成/待评价。买方和卖方的状态是对立的，这里的卖方就是网站本身，商品是虚拟商品，不存在物流，那么商品的属性（详情介绍、价格、图片...）可以在后台进行编辑(包括上下架，设置缺货状态)
> 4、抄袭的网站首页有：毕业论文、普刊、编译。其实你可以完全1:1照抄这几个模块（注意里面的下属子页面），内容需要照抄，但是UI可以比他们做的更加出色
> 5、主色调，期望用更加暖心护眼的色调。
>
> 你可以先重新做需求，然后理数据库，最后再写代码，然后回归。不着急。

| 编号 | 已确认要求 | 本期行为 |
| --- | --- | --- |
| MALL-01 | 自营商城，卖课／服务 | 商品分类→商品列表→详情→立即购买→订单 |
| MALL-02 | 微信／支付宝，手续及 Key 尚未齐全 | 弹出可选渠道的收银台，点击确认模拟成功；订单、金额、渠道、模拟标记在服务端落库 |
| MALL-03 | 买卖双方订单状态、无物流 | 一份订单状态驱动双方视图，履约以课程／服务交付及买方确认完成为依据 |
| MALL-04 | 后台可维护商品 | 名称、类别、课程／服务、简介、详情、价格、图片、详情分节、上下架、缺货均可编辑 |
| MALL-05 | 临摹三类及子页面 | 参考站首页、分类列表、详情与相应子服务逐页建立映射，不仅制作三张入口卡片 |
| MALL-06 | 暖心护眼 | 米白背景、暖棕主色、低饱和辅助色；深色主题采用暖深底，确保主副文字对比 |
| MALL-07 | 先需求再数据再实现回归 | 需求基线→数据库设计→各端实现→业务、权限、幂等、回退、界面回归 |

用户补充：项目仍在开发阶段，直接按当前商城方案实现，不提供双版本入口、版本对比或历史数据兼容升级流程。

## 二、<span id="pages">商品与页面</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 商城首页：三主分类、课程／服务商品卡片、明确价格及库存状态、订单入口。
- 分类子页：分类内商品列表，支持返回首页、重载和无数据占位；不出现参考站其它业务分类。
- 详情子页：本地品牌图／商品图、名称、价格、内容分节、交付说明、商品状态及立即购买；下架或缺货不可新购。
- 下单／收银台：确认商品与人民币金额，选择支付宝／微信渠道，提示“模拟支付，不会扣款”，关闭不支付。
- 买方订单：全部、待付款、待完成、待评价、已完成；可查看订单快照、支付记录、站方交付、确认完成及评价。
- 站方后台：商品列表及编辑表单，上下架和缺货开关；订单列表及开始服务／提交交付动作。

参考目标为[**氪研学术**](https://www.keyan.asia/)及其[学术产品服务页](https://www.keyan.asia/productService/)。公开页面的结构、通用名称、可核实价格等事实用于映射；完整长篇营销原文、人物、商标、评价与资质不擅自冒用。实际已核实页面及无法访问的子页另列证据，不把未进入页面写成已逐页复刻。

<span style="color:#d32f2f;">【不确定 M-Q01】用户要求内容照抄，但当前没有参考站长篇文案及图片的所有权／授权材料。先保留分类、子服务事实及信息层级，商品详情由后台完整编辑；不可访问的正文和正式经营价格不能用猜测伪装为原站内容。</span>

## 三、<span id="states">订单与双方状态</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

> 用户提到的待付款等属于订单交易状态；上下架、缺货属于商品状态，分别管理。

| 订单状态 | 履约子状态 | 买方视图 | 站方视图 | 允许动作 |
| --- | --- | --- | --- | --- |
| pending_payment | pending | 待付款 | 待买方付款 | 买方支付／取消 |
| pending_completion | pending | 待完成 | 待开始服务 | 站方开始服务或交付 |
| pending_completion | in_progress | 待完成（服务中） | 待完成服务 | 站方提交交付 |
| pending_completion | delivered | 待完成（待确认） | 待买方确认 | 买方确认完成 |
| pending_review | delivered | 待评价 | 待买方评价 | 买方评价 |
| completed | delivered | 已完成 | 已完成 | 只读订单与评价 |
| cancelled | pending | 已取消 | 已取消 | 只读；本期仅未付款订单可直接取消 |

确认完成后订单已完成履约，待评价是评价阶段；不以发货／签收快递作为节点。不新增自动确认、自动评价、物流单、多商家、分佣或购物车等未要求规则。已付款取消及退款继续作为后续商议流程，不伪造退款到账。

下单时在同一事务校验商品版本、上架与库存、人民币价格，写入完整商品快照。后续改价、下架及缺货不改变历史订单；已生成待付款订单按快照付款。修改价格与下单并发时拒绝旧商品版本，提示重新确认。金额使用整数分，初期数量固定为1。

## 四、<span id="payment">临时支付及真实渠道接口</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

当前支付驱动为 mock，渠道为 alipay／wechat。买方主动点击收银台确认后，服务端按订单应付金额记一笔带模拟标记的成功记录，并进入待完成；前端展示支付成功并可查看订单。重复点击、超时重试及并发支付均不得重复产生订单或收款。

没有商户参数时只能展示应用内支付宝／微信渠道收银台，不能凭空生成有效官方支付单或官方付款二维码。真实外部 App／SDK 唤起留在渠道驱动边界；正式商户资料到齐后再接创建预支付、签名验签、渠道回调、主动查单、对账及退款。真实模式不能接受客户端“成功”直接改已付款，也不能失败后静默使用模拟驱动。

<span style="color:#d32f2f;">【不确定 M-Q02】“跳出支付宝／微信”是否还要求无商户订单情况下唤起外部 App，当前无法等价于有效收银台；本期交付可操作的渠道弹窗和模拟付款，外部正式唤起须随商户配置按各端渠道能力验收。</span>

## 五、<span id="data">数据库与接口约束</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

采用 [**Go**](https://go.dev/) 后端、文件原子快照与可选 [**PostgreSQL**](https://www.postgresql.org/) 聚合事务。商城商品、订单、支付／评价和幂等收据构成实际运行模型；字段字典与事务约束见[数据库设计](../数据库设计/数据库设计.md)。

| 资源 | 接口（前缀 /api/v1） | 约束 |
| --- | --- | --- |
| 商品目录 | GET /products、GET /products/{id} | 游客可见已上架商品；缺货仍可浏览 |
| 商品维护 | GET／POST /admin/products、PUT /admin/products/{id} | 管理员；修改提供 expected_version |
| 下单 | POST /shop-orders | 客户；product_id、product_version；金额由服务端决定 |
| 订单查询 | GET /shop-orders、GET /shop-orders/{id} | 客户只看本人，管理员看全部 |
| 订单动作 | POST /shop-orders/{id}/actions | action、expected_version；按角色及当前状态校验 |

写请求使用 Idempotency-Key；同键同请求返回原结果，同键不同请求拒绝。订单动作含 pay、start、deliver、accept、review、cancel；支付提供 channel，交付／评价提供 text，评价还需 rating（1—5）。订单状态、支付记录、快照、幂等结果在同一事务持久化。

按当前商城结构初始化开发及测试数据，不增加历史版本兼容与升级流程。回归使用独立测试数据，不清理正在运行的服务数据。

## 六、<span id="quality">界面、回退及验收</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 商品与订单列表均需完整空态、重载及出错后可继续操作的本地演示；进入／刷新／写操作优先请求API，短超时可配置，后续成功响应自动恢复真实数据。
- 页面与支付弹窗适配白天、黑夜、跟随系统；提供简体中文、繁体中文、藏文、英文、日文、法文、西班牙文、德文、俄罗斯文、韩文切换。动态商品内容保留后台输入语言。
- 商品图默认复用本地品牌图兜底；后台维护的合法商品图片加载失败保留品牌图。新增素材按项目来源及许可清单登记，不使用参考站无授权宣传素材。
